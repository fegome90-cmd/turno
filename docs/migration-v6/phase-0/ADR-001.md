# ADR-001: migración aislada de Turno a React y Base UI

**Estado: propuesta para fase 0; precisiones D1–D6 aceptadas el 08/11/2026 ([ACCEPTANCE](ACCEPTANCE.md)); aceptación global pendiente de firma.** No autoriza implementar, instalar, publicar producto, integrar ni desplegar. Fuente: [PLAN, secciones 1–4](../PLAN.md); ejecución y referencias en [FASE_0](../FASE_0.md).

## Intención y límites

Conservar comportamiento, identidad, accesibilidad y movimiento del prototipo v5 al portar a React/Base UI. La referencia v5 se conserva sin cambios y con su discrepancia histórica de suite visible. El resultado objetivo es una demo autónoma de datos sintéticos en memoria, perfil público Demo, sin backend, autenticación, API ni persistencia. No es una release ni un widget integrado.

## Arquitectura propuesta

Una aplicación nueva en `prototypes/frontend-v6/`, un root React y un dueño por estado. Dominio/adaptador sintético separados de UI; puerto explícito sin SDK de backend. Tema solo de sesión, sin escribir storage. Primitivas Base UI y CSS antes de otra dependencia de movimiento. El plan define interfaces y destinos; ninguna ruta v6 se crea al preparar este ADR.

React 19, TypeScript, Vite, Base UI y dependencias propuestas en el plan. Versiones exactas y compatibilidad deben revalidarse y fijarse en un lock de producto durante 1A autorizada. Lo ensayado en fixture no está instalado en producto; Compiler es opcional posterior y Oxc experimental queda fuera de la base. No se adoptan upgrades por redactar esta decisión.

## Alternativas y consecuencias

| Opción | Consecuencia | Estado en el plan |
|---|---|---|
| Portar dentro de v5 | Pierde referencia inmutable y mezcla historial/artefactos | Descartada |
| Convivir React/vanilla sobre el mismo DOM | Doble autoridad sobre foco, historial y lifecycle | Descartada |
| Nueva v6 aislada | Duplica temporalmente referencia y candidato, permite comparación y vuelta segura | Recomendada y prevista; no implementación aprobada |

No se reabre el framework ni Base UI. Las precisiones de implementación que necesitan decisión están en [ACCEPTANCE](ACCEPTANCE.md). Ante una brecha fundamental de Sonner, STOP y alternativa acotada con decisión, sin degradar la pila v5 ni sustituirla tácitamente.

## Condiciones y evidencia

G0 exige baseline resuelto, 212 identidades preservadas y plan/precisiones aceptados. No se cuentan pruebas DOM como navegador o dispositivos/AT. Cada fase registra comandos, códigos, SHA/huella y artefactos; ante FAIL/BLOCKED requerido se detiene la dependiente. Fase 0 identifica referencia y artefacto de retorno sin llamarla estable; G7A ensaya reapertura en sandbox, sin despliegue y sin conservar sesión tras recarga.

## Decisiones aceptadas por el dueño

D1–D6 (08/11/2026) y D7–D9 (08/11/2026, de la auditoría con el router de diseño), detalladas en [ACCEPTANCE](ACCEPTANCE.md): tema de sesión propio; Popover no modal; el dominio valida; Sonner con adaptador y brecha que bloquea; Chromium obligatorio y el resto por separado; demo autónoma; gestor general con «Lista»; identidad visual en una fase posterior a la paridad; movimiento idéntico a v5.
